# Layer 2: road demand

Layer 1 produces hourly vehicle counts per junction. Layer 2 turns them into flows on every road and turn of a configured network. It does not depend on SUMO.

| Module | Contents |
|---|---|
| `trafficgen.config.network` | Network config, `load_network_config`, `build_road_demand_generator` |
| `trafficgen.config.network_validations` | Checks of the network config |
| `trafficgen.config.toml_tables` | Turning TOML tables into dataclasses |
| `trafficgen.models.road_demand` | `RoadDemandModel`, the layer 2 generator |
| `trafficgen.balancing.network_balancing` | `NetworkBalancer`: fits the entry flows and computes the flows on every road |
| `trafficgen.balancing.result` | The result, `RoadDemand`: builds the five output tables and its warnings (`RoadDemand.from_flows`) |
| `trafficgen.utils.optimization` | Non-negative least squares per hour |
| `trafficgen.utils.tables` | Generic helper for long-format hourly tables |

## Config

A network config adds `[[roads]]` and `[[turns]]` to the `[[junctions]]` of layer 1. Examples: `configs/network_single.toml`, `configs/network_grid_2x2.toml`. Every value is a modelling assumption, since the data has no roads, lanes or turns.

| Key | Where | Default | Meaning |
|---|---|---|---|
| `from`, `to` | `[[roads]]` | | Without `from` the road enters the network, without `to` it leaves it |
| `weight` | entry roads | required | Share of the entry flow of the junction. Sums to 1 per junction |
| `through_share` | internal roads | 1 | Share of vehicles that reach the end of the road |
| `length_m`, `lanes`, `speed_limit_kmh` | `[[roads]]` | none | Only used for the travel time and capacity warnings |
| `ratio` | `[[turns]]` | required | Share of vehicles on `from_road` that continue on `to_road`. Sums to 1 per road |
| `scale` | top level | 1 | Multiplier of the layer 1 counts |
| `weighting` | `[balance]` | `absolute` | `absolute` fits differences in vehicles, `relative` divides them by the requested count |
| `tolerance_vph` | `[balance]` | 0.5 | Larger differences mark an hour as unbalanced |
| `max_travel_time_fraction` | `[balance]` | 0.1 | Warn, once when the config is created, when the free-flow travel time exceeds this share of an hour |
| `lane_capacity_vph` | `[balance]` | 1800 | Warn after balancing when the flow per lane exceeds this |

Road ids should be the edge ids of the SUMO network. Invalid configs fail with a message naming the file and the problem.

### Generating a config

Both configs in `configs/` are generated by `scripts/generate_network_config.py`, and the first lines of each file hold the command that wrote it. Regenerate a config instead of editing it by hand; a test checks that the committed files match their commands.

A grid of rows x columns. Junctions are numbered row by row, outer arms get an entry and an exit road, neighbours get one road in each direction:

```bash
uv run python scripts/generate_network_config.py grid --rows 2 --cols 2 --length-m 300 --lanes 1 --speed-limit-kmh 50 --output configs/network_grid_2x2.toml
```

From a SUMO network, so that road ids are its edge ids. Dead-end nodes are the boundary, every other node needs `--junction NODE=JUNCTION`. Lengths, lanes and speed limits come from the lanes, turn directions from the `dir` of each connection:

```bash
uv run python scripts/generate_network_config.py from-sumo sumo/scenarios/single-intersection/intersection.net.xml --junction J0=J1 --output configs/network_single.toml
```

Both modes take `--turn-ratios RIGHT STRAIGHT LEFT` (default 0.15 0.7 0.15, no U-turns; when a direction is missing the others share its ratio) and `--data-template` (default `../data/processed/kaggle_junction_{number}.csv`, where `{number}` is the junction's position). Entry roads of a junction share its entry flow equally.

## Model

The flow `f_r` of a road is the number of vehicles per hour that reach its end. With `E_j >= 0` the traffic entering the network at junction `j`:

```
entry road r of junction j:  f_r = weight_r * E_j
internal or exit road r:     f_r = through_share_r * sum over turns q -> r of ratio * f_q
junction j:                  T_j = sum of f_r over the roads that end at j
```

In matrix form `f = A f + B E`, so `f = (I - A)^-1 B E = (I + A + A^2 + ...) B E`. The k-th term holds the vehicles after k junctions. The junction totals are `T = C f = M E`.

- `M[i, j]` is how often on average a vehicle entering at `j` passes junction `i`. The sum of a column is the mean number of junctions a vehicle passes: 2.0 in the 2x2 grid with 15/70/15 turns. This is why placing every count on the outer roads (`E = counts`) doubles the traffic there.
- `(I - A)^-1` exists and is non-negative when the spectral radius of `A` is below 1, that is when every vehicle can leave the network. The config check rejects closed loops.

## Balancing

For every hour, `min ||W (M E - counts)||^2` subject to `E >= 0` is solved with non-negative least squares (`scipy.optimize.nnls`). `M` depends only on the config. When `M` is square and `M^-1 counts` is non-negative, that exact solution is used directly.

The fit can be infeasible: a small junction next to a large one may receive more vehicles from its neighbour than its own count. Then its entry flow is 0, no flow is negative, and the difference is reported in `junction_balance`, `RoadDemand.unbalanced_hours` and a `RoadDemandWarning`. Turn ratios towards the small junction and `through_share` change `M` and so whether an hour is feasible. Entry weights only move traffic between the roads of a junction.

Flows are rates and need not be integers. Given the counts, the result is deterministic. `RoadDemandModel.sample` gives each junction its own seed derived from the one passed in.

Travel times and flows per lane are reported in the `roads` table and in warnings, but flows are not limited: queues are measured by SUMO.

## Output

| Table | Columns |
|---|---|
| `entry_flows` | `datetime, road, junction, vehicles_per_hour` |
| `road_flows` | `datetime, road, from_junction, to_junction, kind, vehicles_per_hour` |
| `turn_flows` | `datetime, junction, from_road, to_road, ratio, vehicles_per_hour` |
| `junction_balance` | `datetime, junction, requested, achieved, difference` |
| `roads` | `road, kind, from_junction, to_junction, weight, length_m, lanes, speed_limit_kmh, through_share, free_flow_time_s, max_flow_per_lane, hours_over_capacity` |

## Generating

Write the five tables as CSV files to a directory. Warnings go to stderr:

```bash
uv run python scripts/generate_road_demand.py --config configs/network_grid_2x2.toml --start 2017-04-03T00:00 --end 2017-04-10T00:00 --seed 42 --output-dir outputs/grid
```

`--scale` overrides the `scale` of the config. From Python:

The generator is used like the layer 1 models: `build_road_demand_generator` fits a `RoadDemandModel` on the data of every junction, and `sample` can then be called for any time range:

```python
from trafficgen import build_road_demand_generator, load_network_config

generator = build_road_demand_generator(load_network_config("configs/network_grid_2x2.toml"))
demand = generator.sample("2017-04-03", "2017-04-10", seed=42)
demand.road_flows, demand.junction_balance, demand.unbalanced_hours
```

`NetworkBalancer(config).balance(counts)` balances counts that come from elsewhere, one column per junction.
